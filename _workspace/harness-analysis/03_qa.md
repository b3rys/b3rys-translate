## 4. Chrome MV3 manifest · 권한 · 경계면 점검

### MV3 구조

- 생성 manifest의 `manifest_version`은 3이다.
- background는 `service_worker: background.js`로 구성되어 MV3 형태에 맞다.
- 일반 content script는 `<all_urls>`에서 `document_idle`, YouTube MAIN-world bridge는 `*://www.youtube.com/*`에서 `document_start`로 로드된다.
- `externally_connectable`은 선언되지 않아 일반 웹페이지가 `chrome.runtime`으로 background에 직접 연결하는 표면은 기본적으로 열려 있지 않다.

### 권한 위험

manifest 권한:

- `permissions`: `storage`, `activeTab`
- `host_permissions`: Gemini, OpenAI, Anthropic, YouTube 및 `<all_urls>`
- content script `matches`: `<all_urls>`

평가:

1. `<all_urls>` host permission이 개별 API/YouTube host permission을 모두 포괄하므로 개별 항목은 중복이다.
2. 모든 사이트에 content script를 상시 주입하고 모든 URL에 host 접근을 요청하므로 기능상 설명 가능하더라도 Chrome Web Store 심사·사용자 신뢰·침해 시 blast radius 측면에서 가장 넓은 권한 모델이다.
3. `<all_urls>` content script/host 접근이 이미 있으므로 `activeTab`의 실효성은 낮아 보인다. 실제 필요 API별 최소권한 재검토가 필요하다.
4. API key는 실제 코드에서 `chrome.storage.local`에 저장된다. CLAUDE.md의 “storage.sync” 결정 문구와 불일치한다. 구현은 로컬 저장을 명시하고 있어 보안상 더 보수적이지만 문서 드리프트가 있다.

### YouTube MAIN-world bridge

`youtube-bridge.content.ts`는 페이지 전역의 `fetch`와 `XMLHttpRequest.prototype`을 monkey-patch하고 `window.postMessage`로 isolated world와 통신한다.

위험:

- 메시지 수신 시 `e.source === window`, origin, payload shape, requestId 형식 검증이 없다.
- `__b3rys_fetch_request`의 `url`을 검증하지 않고 `origFetch(url, { credentials: 'include' })`로 전달한다. YouTube 페이지 문맥 자체가 가진 권한을 넘지는 않더라도, 프레임/페이지 스크립트와 bridge protocol이 충돌하거나 악용될 수 있는 confused-deputy/안정성 표면이다.
- 전역 fetch/XHR 패치는 YouTube 구현 또는 다른 확장과 충돌할 가능성이 있으며, 이를 실제 Chrome에서 검증하는 E2E 테스트는 확인되지 않았다.
- `console.log/error`가 production content script에 다수 남아 있다.

## 5. content ↔ background 메시지 타입 점검

장점:

- `utils/messaging.ts`에 discriminated union으로 `BackgroundMessage`와 `ContentMessage`가 분리되어 있다.
- background listener는 `BackgroundMessage`를 받고 네 가지 요청(`TRANSLATE_BATCH`, `CACHE_LOOKUP`, `OPEN_POPUP`, `CLEAR_CACHE`)을 분기한다.
- 응답 타입도 `TranslateBatchResponse`, `CacheLookupResponse`, `ClearCacheResponse`로 선언되어 있다.

위험/한계:

1. 타입 안전성이 listener 내부와 응답 변수 annotation에 주로 머문다. 다수 `chrome.runtime.sendMessage({...})` / `tabs.sendMessage({...})` 호출은 request 객체를 `satisfies BackgroundMessage/ContentMessage` 또는 typed wrapper로 검증하지 않는다. 송신 타입이 수신 union과 드리프트해도 컴파일러가 놓칠 수 있다.
2. Chrome 메시지는 런타임 `any`인데 payload schema 검증이 없다. `paragraphs`, `mode`, language code, 문자열 길이/배치 크기, sender를 background 경계에서 확인하지 않는다.
3. `selectedEngine`은 storage 값을 타입 단언만 하고 런타임 enum 검증 없이 `getEngine`에 전달한다. 손상된 storage 값이면 `undefined.translate` 오류로 이어질 수 있다.
4. unknown message에 명시 응답/오류가 없고, `OPEN_POPUP`은 타입화된 response union과 별개로 비동기 결과를 호출자에게 전달하지 않는다.
5. background 및 실제 송수신 계약을 직접 import/실행하는 테스트를 찾지 못했다.

## 6. 번역 엔진 경계 점검

장점:

- `TranslationEngine.translate` 인터페이스와 `EngineType` union으로 Gemini/OpenAI/Anthropic 구현을 한 registry 뒤에 둔다.
- 공통 prompt builder, response parser, retry helper를 재사용한다.
- API 호출은 background service worker에 집중되어 content script에 key를 직접 넘기지 않는다.
- 429/5xx 및 네트워크 오류에 exponential backoff가 있다.

위험:

1. **엔진 구현 직접 테스트 부재**: Gemini/OpenAI/Anthropic adapter의 URL/header/body, provider별 오류/usage parsing, 빈 응답을 mock fetch로 검증하는 테스트를 찾지 못했다.
2. **background orchestration 테스트 부재**: API key 누락, cost limit, rate limit, cache hit/miss, usage flush, 동시 요청을 직접 검증하지 않는다.
3. `cacheKeyPrefix()` 주석은 target language + mode를 포함한다고 하나 실제로는 `word`만 별도 prefix를 쓰며 `page`와 `subtitle`은 같은 key를 공유한다. 서로 다른 prompt 정책의 결과가 교차 재사용될 수 있다. engine type도 cache key에 없어 엔진 변경 후 이전 엔진 결과가 재사용된다.
4. provider response는 수동 TypeScript interface와 `response.json()`에 의존하며 런타임 schema 검증이 없다. 비-JSON 오류 본문, provider schema 변경, 부분 응답은 일반 예외/빈 번역으로 귀결될 수 있다.
5. fetch timeout/AbortSignal이 없어 네트워크가 장시간 pending일 때 service-worker 요청이 묶일 수 있다.
6. 여러 동시 batch가 cost-limit 사전검사를 함께 통과할 수 있어 설정 한도를 초과한 뒤에야 집계될 수 있다. 현재 limit은 엄격한 트랜잭션 경계가 아니라 soft backstop이다.
7. 최종 429/5xx 재시도 소진 시 provider/status 정보 대신 일반 `Request failed after retries`가 될 수 있어 진단성이 낮다.
